### The same coins can be spent twice: the portal and the Daily 10 box keep separate spend ledgers over one pool of points

`src/lib/portal/reward-actions.ts:46` (high)

- **What goes wrong:** A student has earned 400 points (student_point_awards). In the portal's Rewards they open a box for 250, so portal_rewards.spent becomes 250 and the portal shows 150. Then they finish a Daily 10, which the portal links to (/learn/daily-ten). DailyTenEnd reads the old ledger, which ignores portal_rewards: it shows '400+ tokens to spend' and offers 'Open it' because the old balance is at least 300 (DailyTenBox.tsx:39, 140). PrizeReveal then calls open_reward_box, which spends 300 from the same points (20261112231500_rewards.sql:100-106 subtracts only student_reward_boxes). Result: 550 coins spent from 400 earned, and the two screens show two different balances. The reverse also works: coins spent in the portal can still be spent on Daily 10 boxes. Boxes opened before the swap on the deleted /dashboard/student/rewards page are not subtracted in the portal either. The deleted Progress page did subtract them (loadOpenedBoxes); the new code dropped that, so those coins come back to be spent again.
- **Fix:** Keep one balance for the one pool, and make every spend atomic.

1. **A new migration** adds a SQL function, for example `portal_spend(p_student, p_price, p_next jsonb)`.
   - It takes the same advisory lock as `open_reward_box`: `pg_advisory_xact_lock(hashtextextended('reward-box:' || p_student, 0))`.
   - It computes the balance as `SUM(student_point_awards.points) - SUM(student_reward_boxes.cost - bonus) - portal_rewards.spent`.
   - Only when that balance covers the price does it raise `spent` and write the new `owned`/`passes`.
   - `spend()` in reward-actions.ts calls this function instead of reading and then upserting. This also fixes a second race: two tabs can both read `spent = 0` and both write 250, losing a charge and a prize.

2. **`loadRewards`** subtracts the old boxes' net cost (`balanceOf(lifetime, await loadOpenedBoxes(clerkId))`, then minus `row.spent`). Boxes opened before the swap then stay spent.

3. **The Daily 10 end stops spending.** The founder made coins the only currency, spent only on Rewards.
   - Remove the "offer" and "prize" steps from `DailyTenBox`: no `PrizeReveal` or `open_reward_box` call after a Daily 10.
   - Remove the "tokens to spend" line in `DailyTenEnd`, or feed it the portal's coin balance.
   - If the old box must stay for now, `CREATE OR REPLACE open_reward_box` so it also subtracts `portal_rewards.spent` under the same lock.

### A failed read of portal_rewards counts as 'no row yet', and the next write erases the student's items, passes and spending

`src/lib/portal/rewards.ts:71` (medium)

- **What goes wrong:** A student owns 16 items and 2 passes and has spent 4,000 coins. They change their outfit. 600 ms later Rewards.tsx sends actionWear. The portal_rewards select returns {data: null, error} because of a passing 5xx, a timeout or a network failure (supabase-js returns such errors instead of throwing). loadRewardRow ignores the error and returns {spent: 0, owned: [], passes: {}}. actionWear then filters the outfit down to {} and save() upserts that whole row (reward-actions.ts:92-98). All items and passes are erased for good, and 4,000 spent coins are handed back. The same happens in spend() (reward-actions.ts:45-50): the row is overwritten with owned=[prize] and spent=250.
- **Fix:** 1. In `loadRewardRow`, check for errors. Use `const { data, error } = await db.from('portal_rewards').select(...).eq('student_id', clerkId).maybeSingle(); if (error) throw error;` and remove the `.then(r => r, () => ({data: null}))` wrapper. Only `data === null` with no error means there is no row yet. The display path (`loadRewards`) can catch the error itself if the page should still show something.

2. With that change, `spend()` throws before writing. Rewards.tsx `spendReal` already catches the error and tells the student "No coins were spent".

3. `actionWear` should return `{ok:false}` without writing when the read fails. It should also write only its own columns: `upsert({ student_id: clerkId, face, outfit, updated_at })`. Merge-duplicates then updates only those columns, and the column defaults fill the rest when the row is new.

4. A related problem the same fix would help with: `spend()` and `actionWear` both read the whole row, change it and write it all back. Two of them running at once can overwrite each other. Doing the spend as a single conditional update, through an RPC or with `.eq('spent', row.spent)` checked against the row read, would close that gap too.
